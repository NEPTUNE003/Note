## 一、FreeRTOS 是什么

FreeRTOS 是一款实时操作系统（RTOS，Real-Time Operating System）。区别于 Windows、Linux、macOS 等通用操作系统以用户为先，它更追求**及时性**。

- 相同优先级任务按**时间片**轮询执行；
- 高优先级任务会**打断**低优先级任务；
- 高优先级任务主动放弃 CPU（阻塞或挂起等）时，会让次优先级的任务先执行。

## 二、任务状态

FreeRTOS 中的任务有四种状态：

| 状态 | 说明 |
|------|------|
| 运行（Running） | 正在占用 CPU 执行 |
| 就绪（Ready） | 随时都能执行，等待被调度 |
| 阻塞（Blocked） | 等待延时或信号量等 |
| 挂起（Suspended） | 相当于暂停 |

## 三、调度与上下文切换

调度器本质上是一个中断服务函数，对应的中断是 **PendSV（Pending Service Call）**。上下文切换由 PendSV 中断完成，调度器是决定"下一个跑谁"的算法，PendSV 是执行切换的机制。

- PendSV 可以手动触发；
- 可以在中断里面使用（触发 PendSV，让其在中断结束后再执行任务切换）。

通过 **SysTick** 计时：
1. 每个时间中断让 tick + 1；
2. 判断有没有阻塞列表里的任务时间到了，可以换到就绪列表；
3. 判断是不是该就绪列表里其他任务执行了；
4. 判断 PendSV 挂起位有没有置 1（**真正的上下文切换是在 PendSV 里完成的**）。

**上下文切换**时，为了方便下次从断掉的地方继续执行：
- 将 A 的数据从 CPU 拷贝到 A 的任务堆栈；
- 执行 B 时先恢复，将 B 的任务堆栈的数据取到 CPU；
- 时间到了就保存回堆栈，去执行 A 时再恢复……

## 四、裸机开发 vs FreeRTOS

### 纯裸机开发方案

**1. 依靠主循环**
- 按键响应迟钝，串口打印不准

**2. 主循环 + 定时器**
- 响应稍快，但仍会阻塞按键、UART

**总结：** 裸机开发实现多任务，不能并发、无统一优先级管理、管理混乱、依赖标志位。

### 使用 FreeRTOS 操作系统

- **相对延时（vTaskDelay）**：响应快，串口打印基本准确
- **绝对延时（vTaskDelayUntil）**：响应快，串口打印完全准确

**总结：** FreeRTOS 使用调度器通过时间片轮询和抢占优先级实现多任务并发执行。

## 五、内存管理

### 总堆（Heap）
FreeRTOS 分配的一块连续内存，本质是数组。使用 heap_1.c - heap_5.c 管理堆的分配（一般使用 heap_4.c）。

### 任务栈
每个任务独立拥有，用来存储任务信息（被打断时保存的现场信息等）。可动态分配（自动申请）或静态分配（用户指定）。

### 栈 / 堆大小评估
- 通过 **.map 文件**评估，合理分配总堆 heap 大小（.map 在 MDK-ARM → 工程名文件夹里）；
- 通过**水位监控**评估，合理分配数据栈 stack 大小；
- 减少临时变量、函数调用层数（占用内存）；
- `vTaskGetInfo()` 函数可查询堆栈使用情况。

## 六、CubeMX 配置

CubeMX 配置时列表：**任务名称**（是一个字符串）、**入口函数**（是一个可执行的函数）。不同的任务可以有相同的任务名称，但**入口函数不能相同**。

## 七、任务间通信——消息队列

裸机开发使用全局变量传递信息，但在 FreeRTOS 中，使用全局变量读/写很有可能被高优先级任务或中断打断，或者被覆盖写入等。

FreeRTOS 使用 **消息队列** （Queue）通信，特点：
- **拷贝传递**
- **发送与接收解耦**（不需要等待接收）
- 支持一对多、多对一、多对多
- 可实现阻塞任务操作
- 但时间、空间占用大，不可盲目使用消息队列

**例子：**

1. **按键扫描**：扫描到按键结果，`xQueueSend` 放进 `s_key_queue`；`menu_task` 通过 `key_module_receive`（即 `xQueueReceive`）读出来，根据当前界面分发处理。

2. **MQTT 云端命令**：收到云端要执行的事（切屏 / 设置 LED），不自己直接操作，而是 `xQueueSend` 放进 `cloud_cmd_queue`；`menu_task` 用 `xQueueReceive` 读出来，有命令就执行 `handle_cloud_cmd` 切换界面或设置 LED。

### 队列的创建与阻塞
消息队列创建时需指定**项目大小**、**队列长度**。

- 入队时可设置阻塞时间（队列满时的最大等待时间），范围 0 - portMAX_DELAY：
  - 设置为 0：不阻塞，队列不满就入队，满就报错
  - 设置为 portMAX_DELAY：队满时一直等待
- 出队同理（阻塞时间是队列空时的最大等待时间）

### 队列的两种 API
中断上下文和任务上下文的运行时环境完全不同，要使用不同的函数，FreeRTOS 为此提供了两套 API：

- 任务中可以使用 `xQueueSend()`，因为它允许等待（阻塞），例如等待队列有空位时再发送；
- 中断中必须使用 `xQueueSendFromISR()`，因为中断处理函数不能阻塞（不能等待、不能休眠），否则会导致系统响应迟缓甚至死机。

### 队列的传递方式
- **值传递**：将数据复制到队列内部缓冲区
- **指针传递**：将数据的地址放入队列

### 队列集（Queue Set）
队列集是 FreeRTOS 专门提供的机制，用于让一个任务**同时等待多个队列或信号量中的任意一个**变为有效（有消息或可获取）。一个信号量只能被添加到一个队列集中。

## 八、信号量

信号量基于消息队列实现，但用于**状态同步**、**资源计数**，不传输数据，不占用空间。主要用于：
- **同步**（任务什么时候执行）
- **互斥**（判断谁能执行）

分类：

### 1. 二值信号量（Binary Semaphore）
只有空和满两种状态。`xSemaphoreGive()` 提供信号量，`xSemaphoreTake()` 取走信号量。

**例子**（保证 LCD 已经初始化完成的时序流程）：
1. `lcd_task` 里创建信号量（初始无值，`Take` 拿不到）；
2. LCD 初始化完成后 `xSemaphoreGive` 给信号量放一个值；
3. main 里 `lcd_wait_ready()` 调 `xSemaphoreTake` 去拿，拿到（=有值）说明 LCD 好了，然后才继续后面启动菜单任务等。

### 2. 计数信号量（counting semaphore）
**例子：** 有 N 个缓冲区资源，创建 `xSemaphoreCreateCounting(N, N)`，N 是资源份数。任务取资源用 `xSemaphoreTake`（计数减 1），用完 `xSemaphoreGive`（计数加 1）。计数变 0 时，后面再取的任务就阻塞，直到有任务归还。核心就是同时最多允许 N 个任务各占 1 份资源。

### 3. 互斥锁（mutex）
**例子：** I2C 是一条共享总线，同一时刻只能有一个设备在总线上收发数据。AP3216C、XL9555、ES8388 这几个设备驱动可能在多个任务里同时访问总线，所以每次读写前 `Take` 锁、读写完 `Give` 锁，保证同一时刻只有一个设备占用总线，互不干扰。

### 4. 递归互斥锁（recursive mutex）
**例子：**
1. 递归互斥锁**本质还是互斥锁**（保证不同任务之间同一时刻只有一个能画屏幕）；
2. 它比普通互斥锁多出来的能力就是：**同一任务内部嵌套调用时更方便、不死锁**；
3. 用普通互斥锁时，`spilcd_draw_line` 调 `spilcd_draw_point`，后者会死等 `spilcd_draw_line` 释放锁，但它俩都在同一条执行流里，`spilcd_draw_line` 永远没机会走到解锁，于是卡死；
4. 用递归互斥锁时，`spilcd_draw_point` 发现还是 `lcd_task` 这个任务在跑，于是再上一把锁继续执行，执行完解锁，回到 `spilcd_draw_line` 继续跑完再解锁，一共经历两次上锁、两次解锁。

### 优先级翻转
低优先级任务持锁没放，高优先级任务等锁被阻塞，这时一个不相干的中优先级任务抢占了低任务，高任务实际排在了一个无关任务后面，等待时间不可控。

解决就是优先级继承：高任务等锁时，系统把持锁的低任务临时提到同等优先级，让中任务插不了队，低任务尽快出临界区放锁后恢复原优先级。但它不万能，防不了死锁。

## 九、任务创建、删除、挂起、恢复

- **任务创建和删除**：常用于重启（删除函数参数为 NULL，代表删自己），如通信异常时重启通信
- **任务挂起和恢复**：常用于暂停，如按下暂停键时机械手动作暂停

## 十、软件定时器

软件定时器是一种**虚拟定时器**，完全通过软件方式实现定时功能，时间到了，系统就会自动调用预先定义好的**回调函数**。

## 十一、临界区

临界区本质上是一段**不允许被打断**的代码片段，一旦任务进入这个区间，就不允许高优先级任务抢占，也不允许中断打断，直到代码执行完，退出临界区为止。

1. **任务级临界区**：通过 `vTaskSuspendAll()` 暂停任务调度器，此时即使有高优先级任务就绪，也不会切换，直到调用 `xTaskResumeAll()` 恢复调度；
2. **中断级临界区**：通过 `taskENTER_CRITICAL()` 关闭中断（本质是修改 CPU 的 BASEPRI 或 PRIMASK 寄存器），`taskEXIT_CRITICAL()` 恢复中断，期间所有可屏蔽中断都被屏蔽。

## 十二、事件标志组（Event Group）

事件标志组是一个可以存储**多个二进制标志位**的数据结构，可以理解为一个"状态面板"。每个位（bit）代表一个"事件"或"状态"（如 bit0 为"按键按下"，bit1 为"数据接收完成"）。任务可以设置被单个或多个 bit 唤醒。

**例子：** 工程把 BIT0 当作"成功标志"、BIT1 当作"失败标志"。WiFi 回调里拿到 IP 就把 BIT0 置 1，`xEventGroupWaitBits` 读到它即判定成功；若没连上，重连计数在回调里累加，满 5 次仍失败就把 BIT1 置 1，判定 WiFi 连接失败。

### 通用选型对照表

**7 种机制对照：**

| 机制 | 解决的核心问题 | 是否传数据 | 何时选用 |
|------|--------------|-----------|---------|
| 1. 队列 | 任务间传递具体数据 | 是，可按条缓存 | 一方发数据/消息，另一方接收并按顺序处理 |
| 2. 队列集 | 一个任务同时等待多个队列/信号量 | 间接 | 单任务一次监听多个来源，哪个先来就处理哪个 |
| 3. 二进制信号量 | 通知事件（有/无） | 否 | 只表示某件事发生了/可以继续，不传内容 |
| 4. 计数信号量 | 管理资源数量 | 否 | 有 N 份相同资源，取一份减 1，归还加 1 |
| 5. 互斥锁 | 保护共享资源防互斥 | 否 | 多个任务用同一资源，同一时刻只许一个占用 |
| 6. 递归互斥锁 | 保护共享资源，且允许嵌套加锁 | 否 | 加锁的函数内部还会调用其他加锁函数，避免死锁 |
| 7. 事件标志组 | 同步多个独立状态位 | 否 | 同时跟踪/等待多个条件（成功、失败、超时等） |

**快速判断流程：**

1. 要**传数据**吗？
   - 是 → **队列**
   - 一个任务要等多个队列/信号量 → **队列集**
2. 不传数据，只看状态/事件：
   - 只通知一件事 → **二进制信号量**
   - 要数分了几份资源 → **计数信号量**
   - 要保护共享资源 → **互斥锁**；若函数嵌套调用 → **递归互斥锁**
   - 要同时跟踪多个状态/条件 → **事件标志组**

## 十三、CMSIS

**CMSIS（Cortex Microcontroller Software Interface Standard）**：ARM Cortex-M 系列微控制器软件接口标准，是 ARM 为简化软件开发推出的通用接口。

**FreeRTOS CMSIS V2**：是 CMSIS 标准中针对 FreeRTOS 的第二版标准化接口层，只是提供了一套符合 CMSIS 标准的统一 API，让开发者可以用相同的接口调用 FreeRTOS 的功能，也方便在不同 RTOS 之间切换。

## 十四、自旋锁 vs 互斥锁

自旋锁与互斥锁都是为了保护共享资源。区别在于：

- 使用**互斥锁**（mutex）时，CPU 可以去干别的事（A 持有锁，B 想要锁，那就先去执行 C，A 释放锁了再执行 B）；
- 使用**自旋锁**（spinlock）时，CPU 可能会空转（A 持有锁，B 想要锁，那 CPU 就一直等着）。

## 十五、HAL_Delay() vs vTaskDelay()

HAL 库的 `HAL_Delay()` 和 FreeRTOS 里的 `vTaskDelay()`：

1. `HAL_Delay()` 是**阻塞延时**，靠死循环 + 读取 SysTick 计数来实现，在等待期间，CPU 一直在空转，不干任何事。
2. `vTaskDelay()` 是**任务阻塞延时**，它会告诉调度器："这个任务先挂起，时间到了再唤醒我"，在延时期间，CPU 可以去跑其他任务。
3. 如果在 FreeRTOS 任务里用 `HAL_Delay()`，且 FreeRTOS 用的也是 SysTick 作为时钟基准，两者会**冲突**，结果要么延时不准，要么系统卡死，要么任务切换异常。所以在 FreeRTOS 工程里应该用 `vTaskDelay()`，不能用 `HAL_Delay()`。
